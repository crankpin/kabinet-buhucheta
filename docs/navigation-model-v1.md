# Модель навигации v1

Подготовительный документ. Код сайта на этом этапе не меняется.

Пользователю **не объясняем**, что путей три. Три способа существуют параллельно и не мешают друг другу.

Связанные документы: `sitemap.md`, `visual-heritage.md`, `page-types.md`.

---

## 1. Обзор трёх путей

| Путь | Роль | Обязателен? |
|------|------|-------------|
| Обычная навигация | Изучение структуры сайта | Да — основной способ |
| «КТО ВЫ?» | Игровая развилка аудитории | Нет |
| Поиск-подсказчик | Быстрый переход к подготовленной теме | Нет |

Ни один путь не заменяет обзор трёх услуг на главной.

## 2. Обычная навигация

### 2.1. Desktop: вертикальная навигация как фирменный приоритет

Старый сайт использовал фиксированную стеклянную рейку слева (`.hero-nav`).  
Это **приоритетный фирменный вариант для desktop**, который нужно адаптировать под многостраничник — не копировать якоря лендинга один в один.

Текущий горизонтальный sticky-header в `site/` — рабочий каркас до прототипа.  
**Запрещено** удалять идею вертикали без прототипа и сравнения (см. `visual-heritage.md`).

#### Как может работать на многостраничном сайте

- Рейка показывает **5–7 пунктов верхнего уровня**, не весь каталог.
- Клик по пункту ведёт на URL раздела (`/uslugi/`, `/nalogi/`, …), а не только на якорь.
- На главной допускается сочетание: пункт → якорь секции **или** URL раздела — единообразие важнее трюков.
- Вложенные услуги **не** раскрываются полным деревом в рейке: либо короткий flyout/панель «Услуги» (3 ссылки), либо переход на `/uslugi/` с дальнейшим выбором.
- Активный раздел: `aria-current="page"` и визуальный маркер (сдвиг / акцент / короткая линия), без «золотого кипения».
- CTA «Получить консультацию» может жить рядом с рейкой или в её нижней зоне — не дублировать десять раз.

#### Допустимые 5–7 пунктов (черновик)

1. Услуги  
2. Налоги и режимы  
3. Кому помогаем  
4. Полезное  
5. О Карине  
6. Отзывы  
7. Контакты  

География и узкие отраслевые страницы — **не** в верхней рейке (доступ с главной, услуг, подвала) — согласовано с `sitemap.md`.

Почему рейка не должна содержать полный каталог:

- перегруз и потеря сканируемости;
- смешение уровней IA (услуга / отрасль / регион / статья);
- конфликт с поиском-подсказчиком, которому как раз отдают длинный хвост тем.

### 2.2. Пункт «Отзывы»

| Контекст | Куда ведёт |
|----------|------------|
| Пользователь на главной | Якорь блока отзывов |
| Пользователь на внутренней странице | `/` + якорь блока отзывов |

**Канонический якорь сейчас:** `#reviews` (уже в `site` и в меню).

Допустимо позже добавить дублирующий `id="otzyvy"` на тот же блок для человекочитаемости, но **один блок — один смысл**. Не плодить две секции отзывов.

Отдельная страница всех отзывов возможна позже; **не** обязана быть главным пунктом меню. Решение открыто.

### 2.3. Мобильное меню

Вертикальная рейка **не уменьшается** в узкую колонку на телефоне.

На mobile:

- кнопка открытия (бургер) → панель/drawer;
- те же 5–7 пунктов;
- услуги — аккордеон на один уровень (как в текущем каркасе) или список из трёх ссылок;
- контакты / Telegram / WhatsApp в зоне действий меню;
- закрытие: крестик, оверлей, Escape, переход по ссылке;
- корректные `aria-expanded` / `aria-hidden` / `inert` у скрытой панели.

Визуал панели должен наследовать характер (тепло, мягкие поверхности), но не обязан копировать desktop-рейку.

### 2.4. Tablet

Промежуточная зона: либо упрощённая вертикаль, либо усиленная шапка — решение после прототипа. Главное — не держать одновременно и плотную рейку, и перегруженную шапку.

## 3. Интерактив «КТО ВЫ?»

Необязательная навигационная развилка на главной (и только там на первом этапе).

### Правила

- Пользователь **может** пройти сценарий.
- Пользователь **может** закрыть крестиком на **любом** шаге.
- Пользователь **может** нажать Escape.
- После закрытия продолжает пользоваться обычным меню и поиском.
- Развилка **не** заменяет блок обзора трёх услуг.
- Ветки:
  - Я — ИП → `/uslugi/buhgalterskoe-soprovozhdenie-ip/`
  - У меня ООО → `/uslugi/buhgalterskoe-soprovozhdenie-ooo-usn/`
  - Несколько разных организаций → короткий диалог → CTA обсуждения сопровождения

Без JavaScript должна оставаться понятная альтернатива (ссылки на услуги / контакты), даже если диалог «нескольких организаций» упрощён.

## 4. Поиск-подсказчик

Это **не** полнотекстовый поиск и **не** второй Google.

Пользователь вводит начало слова и выбирает тему из заранее подготовленного справочника.

### Пример

Ввод `бухгал…` может показать:

- Бухгалтерское сопровождение ИП  
- Бухгалтерское сопровождение ООО на УСН  
- Бухгалтерия для магазина  
- Бухгалтерия для кафе  
- Самопроверка учёта  

(Точные названия самопроверки — см. варианты в `homepage-content-map-v1.md`; окончательное имя не фиксируем здесь.)

### Рекомендуемая структура `site/data/navigation-index.json`

```json
{
  "version": 1,
  "minChars": 2,
  "items": [
    {
      "title": "Бухгалтерское сопровождение ИП",
      "keywords": ["бухгалтерия", "бухгалтер", "ип", "сопровождение ип", "учёт ип"],
      "group": "uslugi",
      "url": "/uslugi/buhgalterskoe-soprovozhdenie-ip/",
      "description": "Учёт, отчётность и налоги для ИП",
      "priority": 100
    }
  ]
}
```

Поля:

| Поле | Обязательно | Смысл |
|------|-------------|--------|
| `title` | да | Подпись в списке |
| `keywords` | да | Ключи и разговорные синонимы (русский) |
| `group` | да | Группа: `uslugi`, `nalogi`, `otrasli`, `situatsii`, `poleznoe`, `o-karine`, `kontakty` |
| `url` | да | URL или путь с якорем (`/#reviews`) |
| `description` | нет | Короткая подсказка в списке |
| `priority` | нет | Сортировка внутри релевантности (больше = выше) |

### Поведение UI

- Показывать подсказки после **2 или 3** символов (`minChars` в JSON).
- **Не** перенаправлять во время набора.
- Переход только по: клик / касание / Enter на выбранном пункте.
- Клавиатура: стрелки вверх/вниз, Enter, Escape (закрыть панель).
- Группировать выдачу по `group` (услуги, налоги, отрасли, ситуации…).
- Загружать JSON **только после открытия** панели поиска.
- Без внешнего API, БД и нейросети.
- Учитывать опечатки минимально или не учитывать на v1 — важнее хорошие синонимы в `keywords`.

### Где живёт в интерфейсе

Точная геометрия (иконка у рейки / поле в шапке / команда «поиск») — на этапе прототипа.  
Требование: поиск не должен выглядеть как единственный способ найти услуги.

## 5. Согласованность с подвалом и CTA

- Подвал дублирует ключевые разделы и контакты.
- Регионы в подвале — списком; ссылки появляются после создания страниц `/regiony/…`.
- Плавающий контактный объект (ромашка/мандарин) — канал связи, не замена меню.

---

## 6. Производительность и a11y (навигация)

- Меню и поиск — небольшие независимые JS-модули.
- Поиск не в критическом пути первого экрана.
- Видимый `:focus-visible`.
- `prefers-reduced-motion`: без декоративных wipe-анимаций ссылок, мгновенное открытие панелей допустимо.
- Контент разделов индексируется по URL, не только через JS-навигацию.

## 7. Открытые вопросы владельцу

1. Финальная геометрия вертикального меню vs усиленная горизонтальная шапка — после прототипа.
2. Нужна ли отдельная страница всех отзывов в меню.
3. `minChars`: 2 или 3.
4. Где именно якорится кнопка поиска на desktop и mobile.
5. Дата старта зимнего сезона (конец уже ориентир: после 14 января).

---

## 8. Что не делать в реализации без нового задания

- Не внедрять поиск и вертикальную рейку «заодно» с полным редизайном без прототипа.
- Не класть в меню весь `sitemap.md`.
- Не автопереходить по первому совпадению поиска.
- Не объяснять пользователю схему «у нас три навигации».
